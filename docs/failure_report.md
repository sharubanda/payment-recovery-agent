Generated by `scripts/chaos.py --all --write docs/failure_report.md`; re-run with `make chaos`. Every fault in `app/faults.py` is injected at the client boundary where it would happen in production (the LLM client, the Razorpay client, the database engine, the event source), and a real event is run through the real pipeline. The run is deterministic and offline: a throwaway SQLite file per fault, the in-memory Razorpay fixture, no LLM key, a fixed clock (timestamps are offsets from T0) and injected sleeps (backoff waits are recorded, not slept). Nothing here touches the network, and the file is reproducible byte for byte.

How to read a section: **inject** is what was broken; **path** is the stage sequence taken, from the audit rows the run actually wrote; **fallback** is the degrade the code chose; **final state** is what the database holds afterwards; **checks** are the invariants asserted, and the script exits non-zero if any of them fails.

## What this report does not cover

- The live HTTP paths (`LiveRazorpayClient`, `AnthropicLLM`) are not exercised: the faults are injected one layer below them, on the same interfaces they implement, so the pipeline's handling is what is tested, not the wire format of a real 429 or a real API timeout.
- Two processes executing the same pending job at the same instant are not simulated; the single-process scheduler makes that impossible here, and the Razorpay `reference_id` guard shown under `db_unavailable` is what would catch it.
- The `reference_id` uniqueness at Razorpay, the lookup by `reference_id` (`GET /payment_links?reference_id=`) that the reconcile step and the crash probes rely on, the shape of `POST /payment_links/{id}/cancel` and of `GET /orders/{id}/payments` that `order_paid_elsewhere` relies on, are assumptions stated in `FixtureRazorpayClient`. If the real API accepted duplicates, the worst case in the crash-after-send probe would be a redundant link, never a second charge, because a Payment Link only collects money when a customer chooses to pay it; if the lookup answered differently, the reconcile step reports `unknown` and parks the payment for a person instead of minting a follow-up.
