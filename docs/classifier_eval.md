# Classifier evaluation

This set is hand-labelled and partly synthetic, not production traffic: the descriptions are Razorpay's standardised checkout-facing messages as remembered, bank/network messages (ISO 8583, NACH, NPCI) and synthetic or Hinglish variants, and the exact `error_reason` vocabulary Razorpay emits is partially uncertain. The numbers below are the rules' accuracy on this set, nothing more; the rules were tuned against this very set, so a perfect score here is a regression floor, not an estimate of production accuracy, and it says nothing about the class mix or the wording of a real merchant's failures.

Generated by `python scripts/eval_classify.py --write docs/classifier_eval.md` over `tests/fixtures/failure_cases.json`
(118 cases: 103 with an expected class, 15 UNKNOWN by design) against `app/classify.py`.
No database, no network, no LLM: `app.classify.classify` over a PaymentAttempt-shaped object per case.

## About the set

Hand-labelled classifier eval set for app/classify.py. Not production traffic: the descriptions are Razorpay's standardised checkout-facing messages (as remembered, razorpay.com was unreachable while this was written), bank/network messages (ISO 8583, NACH, NPCI, bank-prefixed) and synthetic or Hinglish variants; each note says which. The structured fields are plausible for each case but the exact error_reason vocabulary Razorpay emits is partially uncertain (payment_failed / payment_cancelled / payment_timed_out / card_declined / input_validation_failed / bank_technical_error / gateway_technical_error / server_error / payment_risk_check_failed / international_transaction_not_allowed / transaction_limit_exceeded / insufficient_funds are used here; treat the less common ones as best guesses). expected_class UNKNOWN means the rules must NOT classify the case: it goes to the LLM and then a person. A wrong class is worse than UNKNOWN; tests/test_eval_classify.py asserts zero wrong classifications on this set.
